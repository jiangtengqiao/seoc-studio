## 引言

要理解 Python 为什么长成今天的样子，必须回到它诞生之前的两个背景。一个是荷兰数学与计算机科学研究中心（CWI）的 ABC 语言项目，另一个是同一机构内开展的 Amoeba 分布式操作系统研究。Guido van Rossum 恰好同时身处这两个项目之中，Python 的基因几乎都能在这两个源头里找到对应。

## ABC 语言的教学理想

ABC 语言诞生于二十世纪八十年代初期的 CWI，其设计目标是替代 BASIC 与 Pascal，成为一门面向初学者与各领域研究者的教学语言。ABC 的设计者相信，语言的学习曲线本身就是一门科学问题，因此 ABC 在语法上做了大量减法。它没有类型声明，缩进即代码块，字符串与列表的操作直观而统一。

看一段 ABC 时代的风格遗存就能明白它对 Python 的影响。Python 今天用缩进表达代码块，用高层数据结构作为语言的一等公民，拒绝变量声明仪式，这些决定几乎全部可以在 ABC 中找到先例。

```
# Python  today
def average(xs):
    return sum(xs) / len(xs)
```

这种把样板代码压到最少的取向，正是 ABC 留给 Python 的第一份遗产。

## ABC 的失败与教训

ABC 并没有成功。它在八十年代末期逐渐停止维护，原因值得逐条审视。

第一，ABC 是一个封闭系统。它自带运行环境，却无法方便地调用操作系统能力，也无法与当时已有的 C 语言生态互操作。研究者一旦需要做点真实系统的事，就必须离开 ABC。

第二，ABC 没有可扩展机制。用户不能为 ABC 编写新的底层模块，语言的能力上限被实现者锁死。

第三，硬件条件的限制被误当成语言问题。ABC 的解释器在当时的小型机上运行缓慢，而 ABC 团队没有投入力量做性能工程。

Guido 后来多次在访谈中总结这段经历。ABC 证明了一件事，优雅的教学语言如果不能与真实系统对话，就只能在课堂里存活。这个教训直接塑造了 Python 的架构方向，Python 从一开始就把自己定位为一门可以嵌入系统、可以被 C 扩展的胶水语言。

## Amoeba 项目与系统编程的日常

八十年代中后期，Guido 转入 CWI 的 Amoeba 项目。Amoeba 是一个由 Andrew Tanenbaum 主导的分布式操作系统研究项目，目标是把一组联网的工作站组织成一台逻辑上统一的计算机。

在 Amoeba 团队里，日常的工具语言是 C 与 shell。C 写系统组件精确但冗长，shell 写流程胶水方便却脆弱。Guido 反复体会到两端的撕裂，写一个中等复杂度的系统管理工具，用 C 要花掉与收益不相称的时间，用 shell 又很快撞上表达力的天花板。

这段经历给了 Python 第二个基因。它需要像 shell 一样快地进行系统交互，又要像一门真正的语言一样拥有模块、异常与数据结构。换句话说，Python 的初始问题域不是教学，而是系统管理自动化，只是 ABC 的血统让它天然适合教学。

## 两个源头的汇合

把两条线索放在一起看，Python 的诞生条件就清晰了。ABC 提供了语法层面的理想，简洁、高层、对初学者友好；Amoeba 提供了问题层面的压力，系统编程需要一门更好的胶水语言。1989 年 12 月的圣诞假期，Guido 开始动手写一个新的解释器，作为这两份经验的汇合点。

下一章我们将还原那个假期的具体决策，包括解释器的最初架构、模块系统的雏形，以及 Python 这个名字的来源。

## 本章要点

- ABC 语言证明了缩进语法与高层数据结构在教学上的价值，也证明了封闭生态的失败路径。
- Amoeba 项目提出了真实需求，系统编程缺少一门兼顾速度与表达力的胶水语言。
- Python 的设计从一开始就是两份经验的合流，而非凭空创造。
