## 引言

一门语言活得够久，技术问题终会沉淀为治理问题。Python 的治理史分为两个时代，BDFL 时代与指导委员会时代。分水岭是 2018 年 7 月，Guido van Rossum 在 PEP 572 海象运算符之争后宣布永久休假，事实上退位。本章梳理这一事件的来龙去脉，以及随后建立的新治理结构。

## BDFL 制度的由来

BDFL 是 Benevolent Dictator For Life 的缩写，终身仁慈独裁者。这个半开玩笑的头衔精确描述了 Python 早期的决策结构，PEP 流程公开讨论，但最终拍板权属于 Guido 一人。

这套制度在语言成长期运转良好。它决策快，方向稳定，避免了许多开源项目陷入的委员会设计陷阱。Guido 的品味也经得起时间检验，他否决的提案远多于通过的，Python 的一致性与这种高否决率直接相关。

但 BDFL 制度有两个结构性弱点。其一，它把所有争议的压力集中在一个人身上。其二，它没有继承人机制，制度本身依赖创始人的个人意愿与精力存续。

## PEP 572 之争

PEP 572 提出赋值表达式，允许在表达式内部完成赋值，语法为 `:=`，社区称其为海象运算符。这个提案在技术上并不激进，类似能力在许多语言中存在。

争议在于它触碰了 Python 的可读性底线。反对者认为表达式内赋值会让单行代码承载过多逻辑，违背一行一件事的传统；支持者则给出了循环条件与推导式中的真实收益。讨论在邮件列表与社区媒体上持续了数月，语气逐渐从技术分析滑向立场对抗。

2018 年 7 月，Guido 批准了 PEP 572，随即宣布永久休假。他的退位声明没有指责任何一方，但明确表达了两层疲惫，一是长期作为所有争议的最终仲裁者的疲惫，二是对社区讨论方式恶化的失望。

## 真空与过渡

退位留下了真实的权力真空。谁有权批准 PEP，谁有权决定发布节奏，这些问题一夜之间没有答案。核心开发者团队用了约半年时间讨论新治理结构，先后出现了继续选举新 BDFL、设立三人委员会、设立指导委员会等多种提案。

最终胜出的方案由 PEP 8016 定义，设立五人组成的指导委员会，由核心开发者每年选举产生，任期一年，可连任。委员会拥有最高决策权，但被明确要求尽量少用权力，优先通过委托与工作小组机制运作。日常的技术决策仍由 PEP 流程与各领域专家负责，委员会只在无法达成共识时介入。

## 新制度下的关键判例

指导委员会时代已有若干标志性决策，可以借此观察新制度的气质。

第一个判例是 CPython 治理的日常化。发布经理制度延续，每年一个大版本的节奏在 PEP 602 中制度化，语言的演进从个人节奏变为日历节奏。

第二个判例是性能工程的组织化。2021 年起，Faster CPython 团队以明确目标推进解释器提速，3.11 与后续版本实现了可观的性能提升。这类需要持续多年投入的方向，在 BDFL 时代难以组织，在委员会时代获得了制度性支持。

第三个判例是类型系统的渐进推进。从 typing 模块到模式匹配，争议性特性依旧存在，但决策过程不再围绕单一人物展开，对抗的烈度明显下降。

## 对开源治理的普遍启示

Python 的治理转型是开源史上少有的和平交接样本。它没有分裂出主流分叉，没有发生社区出走。经验可以概括为三点。第一，交接的合法性来自流程而非个人指定，PEP 8016 本身经过完整 PEP 流程产生。第二，新制度刻意限权，委员会被设计成最后手段而非日常管理者，避免了新权力中心的固化。第三，创始人退位后仍以核心开发者身份参与，Guido 后来加入微软并继续为 Faster CPython 工作，为转型提供了连续性。

## 本章要点

- BDFL 制度以高否决率维持了 Python 的一致性，但压力集中且无继承机制。
- PEP 572 之争是导火索，深层原因是单一仲裁者模式的可持续性枯竭。
- 指导委员会制度通过选举产生、刻意限权，完成了开源史上罕见的和平权力交接。
- 新制度已支撑发布日历化与性能工程组织化等长期议程。
