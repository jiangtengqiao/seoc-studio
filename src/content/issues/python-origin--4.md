## 引言

Python 历史上最漫长的一次迁徙，是从 Python 2 到 Python 3 的十二年过渡。这场迁徙从 2008 年 Python 3.0 发布算起，到 2020 年 Python 2.7 正式终止支持才告结束。它是研究语言演化时无法绕开的案例，一次有意为之的不兼容，以及社区为此付出的巨大代价与最终获得的回报。

## 分裂的种子

Python 2 的成功埋下了分裂的种子。九十年代末到两千年代，Python 在系统管理、Web 开发与科学计算三个方向同时扩张，Zope、Django、NumPy 相继出现。语言的用户基数越大，任何不兼容变更的成本就越高。

与此同时，语言内部积累了若干无法向后兼容地修复的缺陷。最核心的是文本模型。Python 2 的 str 类型本质是字节串，unicode 是另一种类型，二者之间的隐式转换制造了无数难以排查的编码错误。随着互联网把全世界文本塞进每一个程序，这个设计缺陷从瑕疵变成了结构性问题。

## Python 3000 计划

Guido 在 2006 年前后正式启动 Python 3000 计划。原则很清晰，既然必须破坏兼容性，就趁这一次把积累的设计错误集中修复，然后长期保持新线的稳定。

主要变更包括以下几项。文本模型重构，str 变为 Unicode 文本，bytes 专司字节。print 从语句变为函数。整数除法语义修正，1/2 得到 0.5。迭代器化，range、map、zip 等返回惰性序列。比较语义收紧，不同类型的无序比较抛出异常。标准库重组与大量旧模块清理。

## 社区的漫长抵抗

Python 3.0 发布后的最初几年， adoption 极为缓慢。原因可以分三层理解。

第一层是生态依赖。大型项目依赖的库动辄数十个，只要链条上有一个关键库没有迁移，整个项目就无法迁移。NumPy 与 Django 的迁移完成时间因此成为整个生态的瓶颈节点。

第二层是感知收益不足。对大量运行良好的 Python 2 系统而言，Python 3 提供的是正确性而非新功能，管理层看不到迁移的商业理由。

第三层是早期版本的性能与工具链问题。Python 3.0 到 3.2 期间解释器性能不占优，迁移工具链也不成熟，进一步削弱了迁移意愿。

## 转折点

真正的转折出现在 2014 至 2016 年。几个因素叠加生效。Python 3.4 与 3.5 带来了 asyncio 与类型标注，新线开始提供旧线没有的实质性能力。主流库相继宣布新功能只在 Python 3 发布。官方明确 Python 2.7 的生命终止日期，并最终定在 2020 年 1 月 1 日。f-string 在 3.6 登场，成为大量开发者日常感知最强的理由。

此后迁移进入收尾阶段。2020 年 4 月，Python 2.7.18 作为最后一个 Python 2 版本发布，一个时代正式落幕。

## 这场迁徙留下的教训

Python 2 到 3 的过渡被后来者反复研究，其中几条教训具有普遍意义。

第一，不兼容变更必须提供清晰的价值叙事。正确性不足以驱动迁移，新能力才可以。第二，生态迁移遵循瓶颈依赖法则，帮助关键库迁移比说服终端用户有效得多。第三，设定并遵守终止日期是可信度的来源，官方最初设定的 2015 年终止期被迫延后，一度损害了信号的可信度，重新确定并坚守 2020 年后，迁移才真正加速。第四，双写兼容期的工具投资回报率极高，six 库与 2to3、现代化工具的成熟显著降低了迁移摩擦。

## 对今天的意义

Python 3 时代的语言治理明显吸取了这段历史。此后的破坏性变更一律走渐进废弃流程，先警告，后移除，跨度多个版本。语言核心团队对兼容性的承诺写入治理文档，任何类似 Python 3000 式的整体断裂都被明确排除。可以说，Python 3 的成功不只是技术修正的成功，更是社区用十二年时间学会如何演化一门语言的过程。

## 本章要点

- Python 3 的不兼容源于文本模型等无法兼容修复的结构性缺陷。
- 迁移缓慢的根因是生态依赖链、感知收益不足与早期版本不成熟。
- asyncio、类型标注、f-string 与明确的终止日期共同构成转折点。
- 这场迁徙的制度遗产是渐进废弃流程与对兼容性的长期承诺。
