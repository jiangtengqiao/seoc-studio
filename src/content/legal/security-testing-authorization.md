# 安全测试授权与范围指引

**最近修订日期：2026年8月14日  生效日期：2026年8月14日**

## 声明与指引性质

本《安全测试授权与范围指引》（以下简称“本指引”）是《网络安全漏洞报告与响应政策》的附属文件，属于该政策第二章“授权范围与限制”的具体操作细则。本指引不独立构成授权，所有安全测试行为必须同时遵守《网络安全漏洞报告与响应政策》和本指引。

**跳转指引**：本指引从属于《网络安全漏洞报告与响应政策》。查看该政策全文请点击：《网络安全漏洞报告与响应政策》。

## 第一章 总则

### 1.1 目的

本指引旨在将《网络安全漏洞报告与响应政策》中关于授权测试范围和操作限制的原则性规定，细化为可执行的具体标准，帮助安全研究人员清晰了解哪些测试行为在授权范围内，哪些行为绝对禁止，减少因理解偏差导致的违规风险。

### 1.2 适用范围

本指引适用于所有基于《网络安全漏洞报告与响应政策》进行安全测试的自然人、组织或其授权的代理人。非基于该政策进行的安全测试行为不适用本指引，仍按《可接受使用政策》及相关法律法规处理。

### 1.3 基本原则

1. **最小测试原则**：测试应以证明漏洞存在为限，不得超出最小必要范围。

2. **数据保护原则**：测试过程中涉及的任何数据必须妥善保护，不得留存、传播或用于测试以外的目的。

3. **实时停止原则**：测试过程中一旦发现可能影响平台正常运行或用户数据安全的情况，应立即停止并通知平台。

4. **报告优先原则**：发现疑似漏洞后，应先通过官方渠道报告，而非继续深入测试或利用。

## 第二章 授权测试的具体范围

### 2.1 允许测试的目标系统

在遵守本指引全部限制条件的前提下，安全研究人员可对以下系统进行测试：

1. **公开可访问的前端页面**：包括官方网站的所有公开页面、文档中心、帮助中心、定价页面、公告页面等。

2. **公开API接口**：平台在API文档中公开发布的接口，以及公开页面中可触达的无需认证的接口。

3. **用户自建测试账号可访问的功能**：使用自己注册的测试账号，在账号权限范围内进行功能测试。

4. **自建测试账号之间的越权测试**：仅限在两个或多个自建测试账号之间测试越权访问（IDOR等），不得涉及他人真实账号。

5. **平台明确标注允许测试的范围**：平台可能在安全公告中公开邀请测试的特定系统或功能。

### 2.2 允许测试的漏洞类型

以下漏洞类型在授权范围内可以测试和验证：

1. **跨站脚本（XSS）**：反射型、存储型、DOM型XSS的验证。

2. **跨站请求伪造（CSRF）**：验证存在CSRF缺陷。

3. **SQL注入**：仅验证注入点存在，不实际提取数据，可使用时间盲注或布尔盲注的最小验证手段。

4. **越权访问（IDOR）**：仅限自建测试账号之间的越权验证。

5. **文件上传漏洞**：仅验证上传点存在风险，上传的文件应为无害测试文件，不包含恶意代码。

6. **信息泄露**：验证系统暴露了本不应公开的信息（如调试信息、目录列表），但不批量获取数据。

7. **配置错误**：如目录可列、权限配置不当、CORS配置错误等。

8. **逻辑缺陷**：如支付逻辑、认证绕过（仅限自建账号）。

9. **其他低风险漏洞**：不涉及数据破坏、不影响服务的漏洞。

### 2.3 禁止测试的系统与数据

以下系统和数据**绝对禁止**进行测试：

1. **生产数据库**：禁止对生产数据库进行任何形式的直接测试，包括SQL注入提取数据、尝试连接数据库端口、尝试获取数据库备份等。

2. **其他用户的账号和数据**：禁止访问、查看、修改、删除其他真实用户的任何数据。

3. **第三方服务商系统**：包括Supabase、GitHub、Cloudflare、支付宝、微信支付、QQ邮箱、AI服务商等第三方平台自身的系统。相关测试应遵循第三方各自的漏洞报告政策。

4. **内部管理系统**：平台的管理后台、内部工具、运营系统等。

5. **物理安全**：公司无对外实体场所，物理安全测试不适用。

6. **支付系统**：支付宝、微信支付的交易流程及平台与支付系统的集成点。测试支付相关漏洞时，仅可使用测试金额（如1分钱）并立即原路退回，不得影响真实交易。

### 2.4 禁止的测试方法

以下测试方法**绝对禁止**：

1. **拒绝服务测试**：包括DDoS、资源耗尽、大量并发请求、无限循环请求等。

2. **暴力破解与撞库**：对任何账号（包括测试账号）的密码进行暴力破解、撞库、密码喷洒。

3. **社会工程学攻击**：钓鱼、伪造页面、冒充工作人员、诱导用户等。

4. **恶意代码上传**：上传病毒、木马、蠕虫、勒索软件等。

5. **漏洞利用链的完整攻击**：只验证漏洞存在，不构造完整的利用链进行攻击。

6. **自动化扫描工具的大规模扫描**：未经平台事先同意，不得使用自动化扫描器（如Nessus、Burp Suite主动扫描等）对平台进行大规模扫描。如需使用，应先获得平台书面许可。

7. **绕过安全措施的专项测试**：以绕过防复制、付费限制、内容过滤等非安全漏洞为目的的测试。

8. **物理入侵或社会工程**。

9. **对未成年用户或数据的任何测试**。

## 第三章 测试数据的管理

### 3.1 测试数据的获取与使用

1. 测试中如需访问数据，仅可访问自建测试账号的数据。

2. 验证信息泄露类漏洞时，如必须展示数据，仅展示最小必要的脱敏样例（如截取部分字段并打码）。

3. 不得下载、导出、保存任何用户个人信息或平台业务数据。

4. 不得将测试数据用于任何个人目的。

### 3.2 测试数据的删除

1. 测试完成后 **24小时** 内，必须删除所有测试过程中产生或获取的数据，包括截图、日志、导出文件、请求记录等。

2. 报告中提交给平台的证据材料，平台接收后按内部流程管理，不视为测试者留存。

3. 删除后如需保留测试记录，应仅保留漏洞描述和复现步骤的文字说明，不保留实际数据内容。

### 3.3 测试账号的处置

1. 测试应使用专门创建的测试账号，不建议使用个人正式账号。

2. 测试完成后，建议注销测试账号。如不注销，应确保测试账号不包含任何个人真实信息。

3. 测试账号产生的数据（如阅读记录、讨论区内容）应一并清理。

## 第四章 与平台的沟通

### 4.1 测试前通知（可选但推荐）

对于计划进行较深入测试的研究者，建议在测试前通过官方邮箱 jiangtengqiao@qq.com 通知平台，告知测试范围和时间窗口。平台收到通知后，可提供必要的配合（如测试环境、白名单IP等），降低测试对生产环境的影响。

### 4.2 测试中紧急情况处理

测试过程中如出现以下情况，应立即停止测试并通过官方邮箱通知平台：

1. 测试导致系统性能明显下降；

2. 测试意外影响了其他用户的数据或访问；

3. 测试发现严重漏洞但无法确认是否被利用；

4. 测试发现系统存在在野利用迹象。

### 4.3 测试后报告

测试完成后，按《网络安全漏洞报告与响应政策》第三章要求提交报告。
