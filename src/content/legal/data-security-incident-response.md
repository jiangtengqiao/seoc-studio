**最近修订日期：2026年8月14日  生效日期：2026年8月14日**

**特别提示**：本政策中关于应急响应流程和时限的承诺，是我们对您的郑重承诺。如发生数据安全事件，我们将严格按照本政策执行，并通过本政策载明的渠道及时告知您。我们建议您定期修改密码、关注账户异常，与我们共同维护数据安全。

## 第一章 总则

### 1.1 编制目的

本政策的编制旨在实现以下目的：

1. **建立健全应急机制**：形成一套完整、可操作的数据安全事件应急响应流程，确保在事件发生时能够迅速、有序、有效地处置。

2. **降低事件影响**：通过快速响应和妥善处置，最大限度减少数据安全事件对用户、平台和社会的影响。

3. **依法合规报告**：依据《中华人民共和国数据安全法》《中华人民共和国个人信息保护法》《网络数据安全管理条例》《网络安全法》等法律法规，履行事件报告和通知义务。

4. **保障用户权益**：在事件发生后，及时告知受影响用户，提供防范建议，保障用户的知情权和补救权。

5. **持续改进安全**：通过事件复盘和总结，发现安全短板，推动安全措施的改进与升级，预防类似事件再次发生。

### 1.2 编制依据

本政策依据以下法律法规、标准及行业最佳实践制定：

1. **《中华人民共和国数据安全法》**（2021年施行），特别是第二十九条关于数据安全事件报告的规定；

2. **《中华人民共和国个人信息保护法》**（2021年施行），特别是第五十七条关于个人信息泄露通知的规定；

3. **《中华人民共和国网络安全法》**（2017年施行），特别是第四十二条关于网络安全事件应急预案的规定；

4. **《网络数据安全管理条例》**（2025年施行），对网络数据处理者的安全事件应对提出细化要求；

5. **《信息安全技术 个人信息安全规范》**（GB/T 35273-2020）等国家标准；

6. **《信息安全技术 信息安全应急响应计划规范》**（GB/T 24363-2009）；

7. 行业最佳实践（如ISO 27035信息安全事件管理、NIST SP 800-61计算机安全事件处理指南等）。

### 1.3 适用范围

本政策适用于本平台所有数据、系统及服务，包括：

1. **数据范围**：用户个人信息（邮箱、密码散列、评估记录、问卷答卷、阅读进度、讨论区内容等）、API调用日志、交易数据、平台运营数据、AI服务交互数据、系统安全日志等。

2. **系统范围**：平台前端页面（GitHub Pages托管）、后端服务（Supabase云数据库及认证服务）、AI服务接口、邮件发送系统、CDN/安全防护系统、第三方服务集成点等。

3. **人员范围**：本公司负责人（JTQ）、所有可能接触用户数据的内部人员、第三方服务提供商及其子处理者（通过合同约束适用）。

4. **场景范围**：任何导致或可能导致数据被非法访问、泄露、篡改、破坏、丢失、滥用的事件，无论是外部攻击、内部疏忽、技术故障还是第三方违规引起。

本政策不适用于以下情形：

1. 第三方平台（如QQ、微信、支付宝、微信支付）自身发生的数据安全事件，相关处理以第三方平台的应急响应政策为准，但平台将积极配合；

2. 用户自身原因导致的安全事件（如主动泄露密码、在公开场合披露个人信息、设备被他人使用等），平台可在能力范围内提供协助，但不承担法定报告义务；

3. 匿名化数据的安全事件（匿名化后数据不属于个人信息，不触发法定通知义务）。

### 1.4 工作原则

本平台在数据安全事件应急响应中坚持以下原则：

1. **预防为主**：通过安全监测、漏洞管理、访问控制、最小授权等措施，尽量预防安全事件的发生，防患于未然。

2. **快速响应**：一旦发现安全事件苗头或确认安全事件，立即启动应急响应，争分夺秒，最短时间内控制事态。

3. **分级处置**：根据事件的性质、影响范围和严重程度，启动相应级别的应急响应，合理调配资源，避免响应不足或过度。

4. **依法报告**：严格按照法律法规规定的时限、内容和方式，向监管机构报告事件，向受影响用户告知情况。

5. **透明告知**：在不扩大风险、不影响安全处置的前提下，向用户充分披露事件信息和处理进展，保护用户知情权。

6. **证据保全**：在处置过程中注意保全证据，为后续调查、责任认定和司法程序提供支撑。

7. **持续改进**：每起事件处置完毕后，认真复盘总结，改进安全措施和应急流程，避免重复发生。

8. **最小影响**：在保障安全的前提下，尽量缩小处置措施对正常服务的影响范围，尽快恢复业务。

### 1.5 术语定义

本政策中下列术语的含义为：

1. **数据安全事件**：指导致或可能导致数据被非法访问、获取、披露、篡改、破坏、丢失、删除、未授权使用或泄露的事件，包括网络攻击、系统漏洞、内部人员违规操作、第三方服务商安全事件等引起的数据安全威胁。

2. **数据泄露**：指受保护的数据被未经授权的主体获取、查看或使用，或数据被公开披露、传输至未授权目的地。

3. **数据破坏**：指数据被意外或故意篡改、损坏，导致其完整性受损。

4. **数据丢失**：指数据因硬件故障、误删除、灾难等原因不可恢复地消失。

5. **数据窃取**：指外部攻击者通过非法手段获取数据，通常以牟利或破坏为目的。

6. **数据滥用**：指有权访问数据的人员超越权限或目的使用数据。

7. **应急响应**：指为应对数据安全事件而采取的一系列措施，包括发现、报告、处置、恢复、总结等阶段的活动。

8. **事件分级**：指根据事件的影响范围、数据敏感程度、可能造成的后果等因素，将数据安全事件划分为不同等级，以决定响应级别和报告义务。

9. **重要数据**：指一旦遭到篡改、破坏、泄露或者非法获取、非法利用，可能危害国家安全、经济运行、社会稳定、公共健康和安全的数据。本平台不属于重要数据处理者，原则上不持有国家定义的重要数据，但参照重要数据保护要求管理核心用户数据。

10. **核心数据**：指关系国家安全、国民经济命脉、重要民生、重大公共利益的数据。本平台不处理核心数据。

## 第二章 组织机构与职责

### 2.1 数据安全应急领导小组

**组成**：由公司负责人（JTQ）担任组长，技术负责人、法务负责人、运营负责人（如有）为成员。鉴于本平台运营主体为小型公司，应急领导小组成员可能由同一人兼任，但职责应明确。

**职责**：

1. 统筹指挥数据安全事件的应急处置工作，作出重大决策；

2. 决定启动、调整和终止应急响应；

3. 决定向监管部门报告的内容和时机；

4. 决定向受影响用户告知的内容和方式；

5. 调配应急响应所需的人力、技术和财务资源；

6. 对事件处置结果进行审核，批准事件总结报告；

7. 对事件责任人作出处理决定；

8. 审批安全改进措施和应急预案修订。

### 2.2 应急响应团队

**组成**：设技术组、法务组、客服组（可由公司负责人兼任，或协调外部资源）。

**技术组职责**：

1. 负责安全事件的监测、发现和初步研判；

2. 执行隔离、遏制、根除、恢复等技术处置措施；

3. 收集和保全技术证据；

4. 分析漏洞成因，提出修复方案；

5. 协调第三方服务商进行协同处置；

6. 验证恢复结果，确保系统安全。

**法务组职责**：

1. 评估事件的法律影响和合规风险；

2. 确定法定报告义务和报告内容；

3. 起草向监管机构的报告和向用户的告知文件；

4. 协调与监管机构、司法机关的沟通；

5. 处理可能的法律纠纷和索赔。

**客服组职责**：

1. 接听用户咨询，向用户解释事件情况；

2. 引导用户采取防范措施（如修改密码）；

3. 处理用户因事件产生的投诉和诉求；

4. 整理用户反馈，向领导小组汇报。

### 2.3 各部门职责分工

| 公司负责人（JTQ） | 全面负责数据安全，审批安全制度 | 担任应急领导小组组长，统筹指挥 |
| 技术负责人 | 日常安全运维、漏洞管理、日志审计 | 技术组组长，执行技术处置 |

| 客服负责人 | 用户沟通、投诉处理 | 客服组组长，用户告知与安抚 |

**说明**：本平台运营团队精简，上述角色可能由同一人兼任，但不得因人员不足而省略关键职责。必要时，平台应引入外部专家（如安全公司、律师）参与应急处置。

### 2.4 外部应急支撑机构

平台与以下外部机构建立应急合作关系：

1. **云服务安全支持**：Supabase、GitHub、Cloudflare等云服务商的应急支持渠道，在事件发生时可通过其技术支持获取日志、协助处置。

2. **安全公司**：可引入第三方安全公司进行取证分析、漏洞修复、恶意代码分析等。

3. **律师事务所**：提供法律咨询，协助起草法律文件，处理监管沟通和诉讼。

4. **司法鉴定机构**：在需要法律追责或诉讼时，委托司法鉴定机构进行电子数据取证和鉴定。

5. **监管机构**：依法向国家网信部门、公安部门、市场监督管理部门等报告，接受指导和监督。

## 第三章 数据分类与分级

### 3.1 数据分类标准

本平台按照数据类型和业务场景，将数据分为以下类别：

1. **用户个人信息**：指以电子方式记录的与已识别或可识别的自然人有关的各种信息，包括：

   - 用户注册信息（邮箱、昵称、密码散列）；

   - 用户行为数据（阅读进度、划重点、浏览记录）；

   - 用户内容数据（评估答卷、问卷作答、讨论区内容、笔记）；

   - 用户交易数据（付款人标识、购买记录、支付核验记录）；

   - 用户设备与日志数据（IP地址、浏览器类型、访问日志）。

2. **AI服务数据**：指用户在使用平台AI功能时输入的提示词、生成的结果、交互记录等。该等数据可能包含用户个人信息，也可能不包含。

3. **API调用日志**：指开发者通过API密钥调用平台服务时产生的日志数据，包括调用时间、接口路径、请求参数摘要、响应状态码等。

4. **交易数据**：指用户与平台之间交易行为的记录，包括订单信息、支付核验、开通记录、退款记录等。

5. **平台运营数据**：指支撑平台运营的内部数据，包括系统配置、安全策略、审计日志、性能指标、匿名化统计结果等。

6. **第三方共享数据**：指从第三方平台接收的数据，如支付平台返回的脱敏交易结果、AI服务商返回的响应。

### 3.2 数据分级标准

根据数据的重要性和敏感性，本平台将数据分为以下三个级别：

| 数据级别 | 定义 | 典型数据举例 |
| --- | --- | --- |
| **核心数据（Level 3）** | 一旦泄露、篡改或丢失，可能对用户权益造成重大损害，或导致平台无法正常运行，或违反法律法规导致严重处罚的数据。 | 用户密码散列、AI服务交互内容、交易核验记录、系统访问凭证、安全审计日志 |
| **重要数据（Level 2）** | 一旦泄露、篡改或丢失，可能对用户权益造成一定损害，或影响平台部分功能正常运行的数据。 | 用户邮箱、用户行为数据（阅读进度、评估结果）、问卷答卷、API调用日志 |
| **一般数据（Level 1）** | 一旦泄露、篡改或丢失，对用户权益和平台运营影响轻微的数据。 | 匿名化统计结果、公开讨论区内容（不含个人标识）、公开文档 |

### 3.3 不同级别数据的安全保护要求

**核心数据（Level 3）保护要求**：

1. **加密存储**：所有核心数据必须以加密形式存储，采用强加密算法（如AES-256）和密钥管理。

2. **传输加密**：传输过程中强制使用TLS 1.2及以上协议。

3. **最小权限**：仅公司负责人或必要人员可访问，访问需认证和留痕。

4. **访问审计**：所有访问行为记录日志，定期审计。

5. **备份与恢复**：定期备份，备份数据同等保护，定期演练恢复。

6. **脱敏显示**：在界面展示时尽量脱敏（如邮箱显示为j***@example.com）。

**重要数据（Level 2）保护要求**：

1. **适当加密**：存储时建议加密，传输时强制TLS。

2. **访问控制**：按需授权，最小必要。

3. **操作留痕**：关键操作记录日志。

4. **定期备份**：至少每周备份一次。

**一般数据（Level 1）保护要求**：

1. 基本安全控制，如传输加密；

2. 访问需合法理由；

3. 定期备份可选。

## 第四章 数据安全事件的分类与分级

### 4.1 事件分类

按照事件的性质和发生原因，数据安全事件分为以下类别：

1. **数据泄露**：受保护数据被未经授权的主体获取、查看、公开披露或传输至未授权目的地。典型场景包括：数据库被攻破导致用户数据泄露、内部人员违规导出数据、第三方服务商安全漏洞导致数据泄露、云存储配置错误导致数据公开。

2. **数据破坏**：数据被意外或故意篡改、损坏，导致完整性受损。典型场景包括：勒索软件加密数据、恶意攻击者篡改数据库记录、误操作导致数据被覆盖。

3. **数据丢失**：数据因硬件故障、误删除、灾难等原因不可恢复地消失。典型场景包括：数据库崩溃且备份缺失、误执行DELETE语句且无备份、云服务商故障导致数据永久丢失。

4. **数据窃取**：外部攻击者通过非法手段获取数据，通常以牟利或破坏为目的。典型场景包括：SQL注入攻击窃取数据、钓鱼攻击获取管理员凭证、API接口未授权访问导致数据被爬取。

5. **数据滥用**：有权访问数据的人员超越权限或目的使用数据。典型场景包括：内部人员将用户数据用于非授权用途、第三方服务商违反DPA使用数据、管理者未按约定用途处理数据。

6. **其他安全事件**：导致数据安全受到威胁的其他事件，如恶意代码感染、社会工程学攻击、物理入侵等。

### 4.2 事件分级

根据事件的影响范围、数据敏感程度、可能造成的后果，数据安全事件分为以下四个等级：

| 事件等级 | 定义 | 典型情形 |
| --- | --- | --- |
| **特别重大（I级）** | 可能造成特别严重的后果，涉及大规模核心数据泄露或国家层面安全风险。 | 全部用户密码散列泄露；核心业务数据库被完全攻破；涉及国家安全的敏感信息被非法获取。 |
| **重大（II级）** | 可能造成严重后果，涉及较大范围用户核心数据泄露或平台核心系统瘫痪。 | 100名以上用户的密码散列或交易记录泄露；AI服务交互内容被大规模窃取；第三方服务商遭受重大攻击导致用户数据泄露。 |
| **较大（III级）** | 可能造成一定后果，涉及一定范围用户重要数据泄露或平台重要功能受损。 | 10-100名用户的邮箱或行为数据泄露；部分API密钥被未授权使用；数据库被短暂未授权访问但未造成大规模泄露。 |
| **一般（IV级）** | 影响范围较小，可快速控制，对用户和平台影响轻微。 | 单用户数据被意外公开；弱密码被碰撞登录单账号；低风险安全告警未造成实际损失。 |

### 4.3 各级事件的判定标准

在判定事件等级时，应综合考虑以下因素：

1. **受影响人数**：数据泄露涉及的唯一用户数量。人数越多，等级越高。

2. **数据敏感程度**：泄露数据属于核心、重要还是一般数据。核心数据泄露的等级高于一般数据。

3. **数据量**：泄露数据的条数、大小。数据量越大，风险越高。

4. **影响范围**：事件影响的是单个账号、多个账号、全部账号，或平台核心系统。

5. **潜在后果**：可能导致的身份冒用、财产损失、声誉损害、法律处罚等后果的严重程度。

6. **事态可控性**：事件是否已被控制、是否仍在蔓延、能否快速遏制。

7. **攻击者能力**：攻击者的技术水平、动机、是否公开披露等。

**定级流程**：发现事件后，由技术组初步研判事件性质和影响范围，提出定级建议；应急领导小组根据建议和判定标准确定事件等级，并据此启动相应级别的应急响应。

## 第五章 监测与预警

### 5.1 安全监测机制与技术手段

平台部署以下安全监测机制和技术手段，主动发现安全威胁：

1. **数据库访问监控**：在Supabase数据库中启用审计日志，监控异常查询、高频访问、越权操作等行为。对可疑SQL语句（如全表查询、批量导出）发出告警。

2. **认证异常检测**：监控登录失败次数、异地登录、异常设备登录、验证码暴力破解等行为。触发阈值时自动触发人机验证或临时锁定。

3. **API调用监控**：监控API密钥的调用频率、调用路径、异常参数等。发现超量调用、绕过限制等行为时自动限流或告警。

4. **静态托管服务安全防护**：GitHub Pages和Cloudflare提供的DDoS防护、WAF（Web应用防火墙）等安全功能，过滤恶意流量、阻断常见攻击。

5. **邮件与域名安全**：监测与平台域名相关的钓鱼活动、伪造邮件、DNS劫持等。

6. **第三方服务安全公告**：关注Supabase、GitHub、Cloudflare、AI服务商、支付服务商的安全公告和漏洞通报，及时评估影响并更新。

7. **定期漏洞扫描**：定期（至少每季度）对平台进行漏洞扫描和安全自查，发现并修复潜在漏洞。

8. **日志集中分析**：将数据库审计日志、访问日志、API调用日志等集中进行分析，通过规则匹配和异常检测发现可疑行为。

### 5.2 预警信息的发布与接收

1. **预警来源**：

   - 平台自身监测系统产生的安全告警；

   - 第三方服务商通报的安全事件或漏洞；

   - 国家有关部门发布的安全预警和漏洞通告；

   - 安全社区、媒体披露的通用漏洞（CVE、CNVD等）；

   - 用户举报的安全问题。

2. **预警分级**：根据预警信息的紧急程度和潜在影响，分为高、中、低三级。

   - **高级预警**：可能导致核心数据泄露或系统被攻破的紧急威胁，须立即处理。

   - **中级预警**：可能导致重要数据风险，需在24小时内处理。

   - **低级预警**：一般安全风险，在常规维护周期内处理。

3. **预警发布**：平台负责人在获知预警信息后，向相关角色发布预警，明确威胁情况、影响范围、建议措施和响应时限。

4. **预警接收确认**：相关角色收到预警后应确认，并按要求执行响应措施。

### 5.3 预警响应措施

收到高级预警时，平台立即采取以下措施：

1. 隔离受影响系统或数据，切断潜在攻击路径；

2. 评估威胁的实际影响，确认是否已发生安全事件；

3. 实施紧急修复或临时缓解措施；

4. 加强安全监测，关注异常行为；

5. 必要时暂停部分服务，待确认安全后恢复。

收到中级或低级预警时，平台根据威胁等级和实际情况，安排相应响应措施。

## 第六章 应急响应流程

### 6.1 发现与报告

**发现**：平台通过以下途径发现安全事件：

1. 监测系统告警；

2. 第三方服务商通报；

3. 用户反馈或投诉；

4. 内部人员发现；

5. 外部渠道（如安全研究机构、媒体报道）披露。

**初步评估**：发现事件后，技术组应立即进行初步评估，确认是否存在异常、涉及的数据和系统范围、是否仍在继续、可能的严重程度。

**内部报告**：事件发现并初步评估后，应立即向应急领导小组报告。报告内容包括：事件发现时间、事件类型、影响范围、初步判断的事故等级、已采取的措施、需要的资源。

**报告时限**：任何可能导致数据安全风险的事件，应在发现后 **30分钟** 内向应急领导小组报告。对于明显属于数据泄露的事件，应立即报告，不得拖延。

### 6.2 先期处置

在正式启动应急响应之前或同时，技术组应立即采取先期处置措施，遏制事态恶化：

1. **隔离受影响系统**：立即断开受影响的服务器、数据库、API接口等的网络连接，防止数据被进一步窃取或破坏。

2. **阻止进一步损失**：暂停受影响服务，阻止数据继续流失；如发现数据正在被下载，切断下载路径。

3. **保护现场**：保留现场数据、日志、系统快照，供后续取证分析。

4. **封禁攻击源**：封禁已确认的攻击IP、账号、API密钥。

5. **通知关键方**：如涉及第三方服务商（如Supabase、Cloudflare），立即联系其应急支持，请求协助（如获取攻击日志、暂停服务、恢复数据）。

### 6.3 事件研判与定级

在先期处置的同时或之后，应急领导小组组织事件研判：

1. **事实核查**：收集并核实事件证据，包括日志、告警、用户反馈、第三方通报等，还原事件经过。

2. **影响评估**：评估事件造成或可能造成的影响，包括受影响数据类别和数量、受影响用户范围、数据敏感程度、潜在后果。

3. **定级确认**：根据第4.2条和第4.3条的标准，对事件进行定级。

4. **定级调整**：随着调查深入和事态发展，如发现事件比初步判断更严重或更轻微，应调整事件等级。

### 6.4 启动应急预案

1. **启动条件**：确认发生数据安全事件（包括疑似事件）时，应急领导小组根据事件等级决定启动相应级别的应急响应。

2. **响应级别**：

   - **I级响应**：特别重大事件，立即启动，公司负责人直接指挥，投入全部资源，协调外部力量。

   - **II级响应**：重大事件，立即启动，公司负责人指挥，协调必要的内外部资源。

   - **III级响应**：较大事件，启动，由技术负责人和法务负责人协调处置。

   - **IV级响应**：一般事件，由技术负责人处置，必要时上报。

3. **预案启动通知**：启动应急预案后，通知相关人员到位，明确职责和任务。

### 6.5 调查与取证

1. **证据保全**：在处置过程中，注意保全证据，包括系统日志、数据库审计记录、网络流量记录、攻击样本、恶意代码等。电子证据应通过哈希校验确保完整性。

2. **原因分析**：分析事件发生的根本原因，包括技术漏洞、配置错误、人为疏忽、第三方安全缺陷等。

3. **影响评估细化**：进一步精确评估受影响的数据、用户范围和潜在后果。

4. **攻防分析**：分析攻击者或肇事者的行为路径、手段、动机，判断是否可能持续威胁。

5. **第三方鉴定**：必要时委托第三方安全公司或司法鉴定机构进行专业取证和分析。

### 6.6 遏制与根除

**遏制**：在调查分析的基础上，采取进一步遏制措施，彻底切断攻击路径：

1. 修复被利用的漏洞；

2. 更新安全策略，阻止同类攻击；

3. 重启或重建受影响系统（在取证完成后）；

4. 增强访问控制，限制可疑主体访问。

**根除**：彻底消除安全隐患，确保不再被同一攻击者利用：

1. 清除系统中的恶意代码、后门、残留文件；

2. 重置被泄露的密钥、凭证；

3. 修复系统漏洞并验证；

4. 更新第三方组件到安全版本。

### 6.7 恢复与重建

在完成遏制与根除后，进行系统恢复与业务重建：

1. **恢复计划**：制定恢复方案，包括恢复的内容、顺序、方法、验证标准。

2. **数据恢复**：从备份中恢复受影响数据，核查数据完整性和可用性。

3. **系统恢复**：逐步恢复系统服务，优先恢复核心业务，再恢复外围功能。

4. **安全验证**：在恢复服务前进行安全测试，确认漏洞已修复、恶意代码已清除、系统安全可靠。

5. **恢复通知**：向用户公告恢复情况，告知哪些服务已恢复、哪些仍需时间。

6. **恢复时限**：力争在事件定级后 **72小时** 内恢复核心业务，**7个工作日** 内恢复全部业务。复杂事件可酌情延长，并向用户公告。

## 第七章 事件通报与报告

### 7.1 向监管机构的报告

根据《个人信息保护法》第五十七条、《数据安全法》第二十九条、《网络安全法》第四十二条、《网络数据安全管理条例》相关规定，发生数据安全事件时，平台应依法向有关主管部门报告。

**报告义务触发条件**：

1. 发生个人信息泄露、篡改、丢失的数据安全事件；

2. 事件可能对用户权益造成损害的；

3. 法律法规规定的其他应当报告的情形。

**报告时限**：

1. **紧急事件（I级、II级）**：在事件发生或发现的 **24小时** 内向有关主管部门报告。

2. **一般事件（III级、IV级）**：在事件确认后的 **3个工作日** 内报告。

3. **进展报告**：事件处置过程中，应定期向主管部门报告处置进展。

4. **总结报告**：事件处置完毕后 **15个工作日** 内提交书面总结报告。

**报告对象**：

1. 国家互联网信息办公室（及其地方机构）；

2. 公安机关（如涉及违法犯罪）；

3. 行业主管部门；

4. 其他依法应当报告的部门。

**报告内容**（参照《个人信息保护法》第五十七条要求）：

1. 事件发生的时间、地点和原因；

2. 事件的性质、涉及的个人信息种类、数量和可能造成的影响；

3. 已经采取的措施；

4. 可能造成的危害及防范建议；

5. 已采取的补救措施；

6. 联系方式及联系人。

**报告模板**：平台应准备标准化的事件报告模板，包括上述内容字段，确保报告及时、规范。

### 7.2 向受影响用户的告知

根据《个人信息保护法》第五十七条，发生或可能发生个人信息泄露、篡改、丢失的事件时，平台应当及时告知用户。

**告知义务触发条件**：

1. 发生个人信息泄露、篡改、丢失事件；

2. 事件可能导致用户权益受损；

3. 法律法规规定的其他应当告知的情形。

**告知内容**：

1. 事件发生的基本情况和可能的影响；

2. 已经采取或将要采取的处置措施；

3. 用户可以采取的防范和补救措施建议（如修改密码、注意钓鱼邮件、开启双因素认证等）；

4. 平台的联系方式。

**告知方式**：平台通过以下方式告知受影响用户（选择一种或多种）：

1. 向受影响用户注册邮箱发送告知邮件；

2. 通过站内信告知；

3. 通过平台首页公告；

4. 如用户联系方式失效，通过公开公告方式（在平台首页显著位置公告）。

**告知时限**：

1. 对于I级、II级事件，应在确认事件后 **48小时** 内告知受影响用户；

2. 对于III级、IV级事件，应在确认事件后 **7日** 内告知；

3. 如事件仍在调查中，可先告知基本情况和初步建议，后续补充详细情况；

4. 出于安全处置需要（如避免引起恐慌、避免干扰调查），经监管机构同意，可适当延迟告知，但延迟不得超过法律法规允许的范围。

**告知模板**：平台应准备标准化的用户告知模板，包含上述告知内容字段。

### 7.3 向社会公众的公告

事件可能造成重大社会影响时（如涉及大规模用户、涉及敏感数据、引起媒体关注），平台应依法或依必要性向社会公众发布公告。

**公告情形**：

1. I级事件；

2. II级事件且受影响用户人数众多；

3. 事件已被媒体报道或引起社会关注；

4. 监管机构要求发布公告的。

**公告内容**：与社会公众告警相关的事件基本情况、已采取措施、对公众的建议、平台联系方式。公告内容应简明扼要、准确客观，避免引发不必要的恐慌。

**公告渠道**：平台官网首页公告、官方社交媒体（如有）、新闻通稿。

**公告时限**：在确认事件重大性后 **24小时** 内发布公告。

## 第八章 事件总结与改进

### 8.1 事件总结报告

事件处置完毕后，平台应编写事件总结报告，内容包括：

1. **事件概述**：事件经过、时间线、影响范围、定级；

2. **原因分析**：根本原因、直接原因、间接原因；

3. **处置回顾**：各项处置措施的执行情况、响应时效性评估；

4. **影响评估**：对用户、平台、第三方的实际影响和潜在影响；

5. **效果评估**：应急响应的效果评估，包括是否存在响应迟滞、协调不畅等问题；

6. **经验教训**：本次事件中暴露的安全短板、流程缺陷、人员不足等；

7. **改进建议**：针对暴露问题提出具体的改进措施、责任部门和时间表。

总结报告应在事件处置完毕后 **15个工作日** 内完成，并提交应急领导小组审核。

### 8.2 责任认定与追究

1. **责任认定**：根据事件调查结果，认定事件的责任方（如平台内部人员、第三方服务商、外部攻击者）和责任程度。

2. **内部责任追究**：对因违规操作、疏忽大意导致事件的内部人员，依据内部管理制度追究责任，包括警告、罚款、解除职务等。

3. **第三方责任追究**：如事件由第三方服务商违约或违规引起，依据数据处理协议追究其违约责任，要求赔偿损失，必要时解除合作并报告监管机构。

4. **外部责任追究**：如事件由外部攻击者导致，依法向公安机关报案，配合司法机关追究其法律责任。

5. **责任追究记录**：责任认定和追究结果应存档备查。

### 8.3 安全措施的改进与升级

根据事件总结报告和改进建议，平台应实施以下安全改进：

1. **技术措施升级**：修复漏洞、更新补丁、加强加密、增加监测点、引入新的安全技术（如双因素认证、数据防泄漏DLP等）。

2. **管理措施完善**：修订安全制度、强化访问控制、细化操作流程、增加审批环节。

3. **人员能力提升**：对相关人员进行安全培训，提升安全意识和技术能力。

4. **第三方管理强化**：对第三方服务商的安全要求进行升级，加强审计和监督。

5. **应急预案修订**：根据本次事件的经验教训，修订本政策，优化应急响应流程。

6. **改进验证**：改进措施实施后，应进行验证，确保有效。

### 8.4 应急演练

为提高应急响应能力，平台应定期组织应急演练：

1. **演练频率**：至少每年组织一次数据安全应急演练。在重大系统变更、重大安全事件后，可增加演练频次。

2. **演练形式**：

   - **桌面推演**：模拟事件场景，讨论响应流程，检验预案合理性。

   - **实战演练**：在测试环境中模拟实际攻击或故障，演练技术处置、报告流程、用户告知等全流程。

3. **演练内容**：涵盖事件发现、报告、定级、处置、恢复、总结全流程，重点检验响应速度、协调配合、报告告知的规范性和时效性。

4. **演练评估**：演练结束后，对演练效果进行评估，发现问题并修订应急预案。

5. **演练记录**：演练过程和评估结果存档备查。

## 第九章 附则

### 9.1 政策的培训与宣贯

1. **培训对象**：所有可能接触用户数据的内部人员，包括公司负责人、技术人员、客服人员、法务人员等。

2. **培训内容**：本政策内容、数据安全基础知识、常见攻击类型识别、应急处置基本操作、报告告知流程等。

3. **培训频次**：至少每年一次培训。新入职人员在接触数据前必须完成培训。

4. **培训记录**：培训活动应留下记录，包括时间、内容、参加人员。

5. **考核评估**：培训后应进行考核或评估，确保参训人员理解并掌握本政策。

### 9.2 政策的更新与审查

1. **定期审查**：本政策至少每年审查一次，评估其适用性和有效性。

2. **触发更新**：发生以下情形时，应及时更新本政策：

   - 重大安全事件后，根据经验教训修订；

   - 法律法规、监管要求变化；

   - 平台系统架构、数据处理方式发生重大变化；

   - 应急演练中发现预案存在缺陷；

   - 监管机构或第三方审计提出改进建议。

3. **更新通知**：更新后的政策在官网公示，并通过公告、邮件等方式通知用户。

4. **版本管理**：每次更新记录修订日期和变更要点。

### 9.6 附件：与第三方服务商的应急协同机制

1. **事件通报协同**：平台与各第三方服务商建立事件通报机制。当任一方发生可能影响用户数据的安全事件时，应立即通报对方。

2. **联合处置**：发生涉及第三方服务的事件时，平台与服务商联合处置，共享必要的技术信息，协同进行遏制、根除、恢复。

3. **证据共享**：双方在合法范围内共享事件调查所需的日志、记录等证据，各自保全。

4. **用户告知协同**：涉及用户告知的，平台为主进行告知，服务商提供必要的技术信息支持。

5. **责任划分**：事件责任按双方DPA和法律法规确定。服务商自身安全事件导致的，由服务商承担主要责任。
